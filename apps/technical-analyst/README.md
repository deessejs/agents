# `apps/technical-analyst`

The first eve agent: an automated engineering digest of GitHub activity for
`env.GITHUB_ORG / env.GITHUB_REPO`, sent by email on a daily and weekly cadence.

Built on the shared workspace packages:

- `@workspace/env` — Zod-validated env at boot (`.passthrough()` so deployment
  variables like `VERCEL_*` and `NODE_ENV` are ignored).
- `@workspace/github` — Octokit + throttling + retry + pagination.
- `@workspace/email` — Resend wrapper + React Email templates + content-derived
  idempotency key.

## Architecture (Eve-native)

```
apps/technical-analyst/
├── agent.ts                  # defineAgent({ model: minimax(env.LLM_MODEL_ID), defaultTools: false })
├── instructions.md           # Role, scope, editorial rules
├── env.ts                    # Zod composition of @workspace/env + agent keys
├── lib/
│   └── state.ts              # eve defineState handles (edition, sourceCorpus)
└── tools/
    ├── collect_activity.ts   # GitHub → source corpus; pause-before-collect
    └── submit_digest.ts      # Validate, render, deliver (Resend idempotency)
schedules/
├── daily-digest.ts           # 0 20 * * * — previous UTC calendar day
└── weekly-recap.ts           # 0 16 * * 5 — current ISO week, Mon → now
```

`defaultTools: false` disables eve's filesystem / shell / network defaults —
the agent advertises only its two business tools. Vercel Cron entries are
auto-generated by `eve build` from each schedule's `cron` field.

## v1 tradeoffs (deliberate)

- **No cross-session persistence.** No KV, no delivery log, no idempotency
  cache. Retries of the same outgoing payload reuse Resend's content-derived
  idempotency key (24h window). Two independently regenerated runs may
  occasionally send a duplicate — acceptable for a single-recipient internal
  digest.
- **Single recipient.** One `DIGEST_RECIPIENT`. No subscription list, no
  `List-Unsubscribe` headers (no endpoint is implemented in this repo).
- **Single repo.** `env.GITHUB_REPO` is one repo. All GitHub endpoints are
  repo-scoped to avoid attributing alerts from other repos to the configured
  one.
- **No `no_reply` opt-in.** A quiet period still produces a recap (the
  renderer shows a quiet-period note + zero counts).

## Tool contract

### `collect_activity({ kind: "daily" | "weekly" })`

- Throws immediately if `process.env.AGENTS_PAUSED === "true"`.
- Computes a **canonical UTC window**:
  - **daily** : previous UTC calendar day `[00:00:00Z, 00:00:00Z)`.
  - **weekly** : **current** ISO week `[Mon 00:00:00Z, now]` (a Friday run
    covers Mon → Fri).
- The window is derived from the canonical UTC date. A retry of the same
  schedule tick reuses the same window and the same editionId.
- Fetches 9 GitHub endpoints (merged PRs via `is:pr is:merged merged:..`,
  open PRs, opened + closed issues, Dependabot, CodeQL, secret-scanning,
  failed CI runs, releases) in parallel. All security endpoints are
  **repo-scoped** (`/repos/{owner}/{repo}/...`).
- Server-side filtering where the endpoint supports it (search endpoint
  `is:pr is:merged merged:start..end`); client-side filtering only for
  endpoints with no server-side date filter.
- Secret-scanning alerts are reduced to `(number, secret_type, state)` —
  the secret value never reaches the model.
- Essential sources (Dependabot, CodeQL, secret-scanning) throw on failure
  so the schedule aborts. Optional sources report per-source availability.
- Truncation: when the search/issues merged-PR endpoint caps at 1000, the
  corpus records the cap as an availability warning so the renderer surfaces
  it. Counts are not presented as complete metrics when truncated.
- Persists `edition` + `sourceCorpus` into session.

### `submit_digest({ kind, report, preview? })`

- Re-checks `AGENTS_PAUSED` defensively.
- Reads `edition` + `sourceCorpus` from session; refuses to render if the
  edition hasn't been collected.
- Validates `report` against a strict Zod schema (4 daily sections / 7 weekly
  sections; each item is `{ text, referenceId }`; sections accept 0..8
  items). Unknown top-level keys are rejected via `.strict()`.
- Resolves every `referenceId` against the corpus. Rejects the call if any id
  is unknown or if a section cites a source kind that isn't in its
  allowlist.
- Renders with React Email (`renderDigest` from `@workspace/email`). URLs +
  titles come from the corpus, not the model. Plain-text output mirrors the
  HTML (annotations + URLs + titles).
- `preview: true` writes the rendered HTML to `tmp/preview-…html` and
  skips both send and any state mutation. Always renders — even for an
  edition that was previously delivered.
- Delivery: `createEmailClient.send(...)` (Resend, `Precedence: bulk` +
  `X-Digest-Id` header, content-derived idempotency key, 24h dedup).
- `endsTurn: true`.

## Edition identity

`editionId = base64url(org | repo | kind | period.start | period.end | recipient).slice(0,24)`
in earlier versions, but the implementation now uses **sha256** over the full
canonical seed. Changing any of the five canonical inputs produces a distinct
24-hex id. Identical inputs always produce the same id. See
`tests/acceptance.test.ts > Edition identity is a real hash of the canonical input`.

## Schedules

| File                              | Cron (UTC)   | Coverage                     |
| --------------------------------- | ------------ | ---------------------------- |
| `agent/schedules/daily-digest.ts` | `0 20 * * *` | previous UTC calendar day    |
| `agent/schedules/weekly-recap.ts` | `0 16 * * 5` | current ISO week (Mon → now) |

Both schedules fire-and-forget a markdown prompt into the agent. The model
is expected to call `collect_activity` then `submit_digest`. If the corpus is
empty AND no optional fetcher reported unavailable, the report is submitted
with zero items; the renderer shows a quiet-period note. Do NOT invent
references.

## Delivery identity + retry

- `editionId = sha256(org|repo|kind|periodStart|periodEnd|recipient).slice(0,24)`.
- Resend idempotency key = `digest:send:<sha256(subject|html|text|to).slice(0,16)>`
  — derived from content. Retries of the same payload reuse the same key.
- A throw from `submit_digest` propagates and the schedule's run is
  unsuccessful (no payload record is preserved).

- `pnpm run check` — oxlint + oxfmt across the repo
- `pnpm run typecheck` — tsc across the repo

## What this agent does NOT do (v1)

- No multi-recipient digests (deferred to v2).
- No inbound email channel — the digest is one-way.
- No auto-fixing of issues / PRs / alerts.
- No non-GitHub data sources (Linear, PagerDuty, Datadog, Sentry).
- No Resend webhook receiver (v2).
- No cross-session de-duplication (Resend 24h window is the only
  safeguard). A rare duplicate of a regenerated report is an accepted v1
  tradeoff.
- No `List-Unsubscribe` headers (no unsubscribe endpoint is implemented).
- No `no_reply` opt-in (a quiet period still produces a recap).
