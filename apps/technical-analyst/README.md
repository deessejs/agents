# `apps/technical-analyst`

The first eve agent: an automated engineering digest of GitHub activity for `env.GITHUB_ORG`, sent by email daily + weekly.

Built on the Phase 1 + Phase 2 shared packages:

- `@workspace/env` — Zod-validated env at boot (this file's `env.ts`)
- `@workspace/github` — Octokit + throttling + 13+ schemas
- `@workspace/email` — Resend wrapper + React Email templates

## Architecture (Eve-native)

```
apps/technical-analyst/
├── agent.ts                  # defineAgent({ model: minimax(...), defaultTools: false })
├── instructions.md           # Role, scope, editorial rules, refusal patterns
├── env.ts                    # Zod composition of @workspace/env + agent keys
├── lib/
│   └── source-corpus.ts      # eve defineState handle for cross-tool data
├── tools/
│   ├── collect_activity.ts   # Fetch GitHub data + project to source corpus
│   ├── submit_digest.tsx     # Validate, render (React Email), deliver (Resend)
│   └── no_reply.ts           # Opt-in no_reply for quiet weeks
└── schedules/
    ├── daily-digest.ts       # defineSchedule({ cron, markdown }) — 0 20 * * *
    └── weekly-recap.ts       # defineSchedule({ cron, markdown }) — 0 16 * * 5
```

The runtime owns scheduling, the model execution loop, session durability, and framework routes. `defaultTools: false` disables eve's filesystem / shell / network defaults — the agent advertises only its two business tools.

Vercel Cron entries are auto-generated by `eve build` from each schedule's `cron` field. No `vercel.json` cron block is needed.

## Tool contract

### `collect_activity({ kind: "daily" | "weekly" })`

- Computes a canonical window:
  - **daily** : `[now - 24h, now]`
  - **weekly**: `[most recent Monday 00:00 UTC, now]` (floored to 5 days)
- Fetches PRs, issues, Dependabot / CodeQL / secret-scanning alerts, failed CI runs, releases (and open PRs) in parallel via `@workspace/github`.
- Projects to a bounded `(id, kind, url, title, meta)` shape and persists into the `sourceCorpus` session state.
- Secret-scanning alerts are reduced to `(number, secret_type, state)` — the secret value itself never reaches the model.
- Returns `{ kind, windowStart, windowEnd, sourceCount, sources: first 50 entries }`.

### `submit_digest({ kind, report, preview? })`

- Reads `sourceCorpus` from session state.
- Validates the structured report with a strict Zod schema (4 daily sections / 7 weekly sections).
- Resolves every `references[].id` against the corpus. Rejects the call if any id is unknown or if a section cites a source kind it isn't supposed to.
- Renders with React Email (`EmailShell` + `DigestBlock` for daily; a generic section block for weekly).
- `preview: true` writes the rendered HTML to `tmp/preview-…html` and skips both send + delivery-record write.
- Normal delivery: `createEmailClient.send(...)` (Resend, RFC 8058 headers, sha256-derived idempotency key) → writes the delivery record to session state.
- Throws on `env.AGENTS_PAUSED === true` so the schedule aborts with a clear signal.
- `endsTurn: true` — the model has nothing more to say once the email is delivered.

## Schedules

| File                              | Cron (UTC)            | Local time                        | Window           |
| --------------------------------- | --------------------- | --------------------------------- | ---------------- |
| `agent/schedules/daily-digest.ts` | `0 20 * * *` (locked) | 22:00 Paris summer / 21:00 winter | previous 24 h    |
| `agent/schedules/weekly-recap.ts` | `0 16 * * 5` (locked) | 18:00 Paris summer / 17: winter winter | Mon → now (≥ 5 days) |

The schedules fire-and-forget a markdown prompt into the agent. The model is expected to call `collect_activity` then `submit_digest`; for quiet weeks, the weekly prompt also has the `no_reply` opt-in.

## Delivery identity + retry

- `digestId = sha256(org | kind | windowStart | windowEnd).slice(0, 8)` — the canonical identifier of the edition.
- The Resend idempotency key is `digest:send:<sha256(subject|html|text|to).slice(0,16)>` — derived from content, not from the model. Retries with the same payload reuse the same key.
- After a successful send, the delivery record (`digestId`, `messageId`, `idempotencyKey`, `sentAt`) is written into `deliveryLog` session state. A retry after a partial-state error reads it.
- A throw from `submit_digest` (Resend reject / paused / unrenderable payload) leaves the delivery log empty, so the schedule's run-finished event shows an unsuccessful run.

## Quality gates

- `pnpm --filter agent-technical-analyst run typecheck` — tsc --noEmit
- `pnpm --filter agent-technical-analyst run test` — vitest run (21 acceptance tests)
- Both must be green before any PR is mergeable.

`eve dev` / `eve build` are the deployment gate. The shipped CLI requires Node.js ≥ 24; CI / production must run on Node 24 to confirm discovery + build.

## Acceptance criteria

The 21 tests in `tests/acceptance.test.ts` cover the PR refactor brief's 10 acceptance criteria. Criteria 1-3 (Eve discovery / build / schedule dispatch) require running the eve CLI; the remaining 7 are exercised directly:

| # | Criterion                                    | Coverage                                       |
| - | -------------------------------------------- | ---------------------------------------------- |
| 1 | Eve discovery with no unresolved diagnostics | `eve info` in CI (Node 24)                     |
| 2 | Real Eve build produces executable output    | `eve build` in CI (Node 24)                    |
| 3 | Native schedule dispatch reaches real tools     | Schedule cron expressions + tool file presence |
| 4 | Distinct daily + weekly behavior under clock | window math tests                              |
| 5 | GitHub event filtering + pagination          | per-helper tests with REST fixtures            |
| 6 | Synthetic secrets excluded from model data   | secret-scanning alert fixture scan             |
| 7 | Fabricated source refs rejected, real links  | resolveReferences logic + corpus url           |
| 8 | Retry after provider acceptance reuses key   | deriveIdempotencyKey + digestIdFor tests       |
| 9 | Preview without delivery-state mutation      | preview branch contract                       |
| 10 | Detectable failure when run doesn't publish    | failure branch contract                       |

## What this agent does NOT do (v1)

- No multi-recipient digests (deferred to v2).
- No inbound email channel — the digest is one-way.
- No auto-fixing of issues/PRs/alerts.
- No non-GitHub data sources (Linear, PagerDuty, Datadog, Sentry).
- No Resend webhook receiver (v2).
- No auto-suppression on bounce (v2).
